## Launch-blocking custody findings

### 1. The supervisor records the wrong process-group identity

`aws_supervisor.sh` backgrounds

`/usr/bin/time ... setsid timeout ... bash "$worker" &`

and assigns `$!` to both `worker_pid` and `worker_pgid`.  `$!` identifies the
outer `time` process; the `setsid` descendant establishes a different session
and process group.  Telemetry and TERM/KILL therefore address an assumed PGID,
not an identity obtained from the actual session leader.

There is a second containment break inside that worker:
`run_singular_stage.py` starts every Singular subprocess with
`start_new_session=True`.  Thus Singular is deliberately outside the worker
process group.  If the outer supervisor kills the worker/stage runner first,
the stage runner cannot execute its own timeout cleanup, and Singular may
survive the supervisor's group kill.

### 2. Orphan evidence is recorded but never gated

The supervisor writes `no_orphan_pgid_census.txt` and
`no_orphan_job_tag_census.txt`, but no subsequent condition requires either
census to be empty or downgrades the terminal when it is nonempty.  Moreover,
the PGID census uses the assumed identity above.  This contradicts the
preregistered statement that any orphan/custody failure is `NO_VERDICT`.

### 3. A generic nonzero worker exit can preserve a mathematical terminal

The worker copies `output/VERDICT.txt` to `TERMINAL_CLASSIFICATION.txt` before
writing the final scope-firewall marker.  The supervisor replaces that terminal
only for swap violation, timeout-like return codes, or a missing/empty terminal.
It does not require `worker_rc==0`.  Therefore any ordinary nonzero exit after
the copy can leave and archive a mathematical classification despite a failed
worker/custody sequence.

### 4. Frozen external expectations need an executable binding

The source-archive, Singular-version, and `elim.lib` expectations arrive only
through environment variables.  This is acceptable only if a separately
reviewed launcher binds those variables to the literal preregistered hashes;
no such launcher is present in this packet.  The repaired runner should either
pin these constants in a source-manifest-covered file or compare the launch
environment against such a file before doing any work.
