## 4. The descended charts: construction, and the threshold that FALLACY-v2 forces

Drivers `box/moh14-20260905/charts14.py` (sizing) and `run_chart.py` (build+run).

**Construction.** The chart logic is the charged `order_basis_full.py`
*verbatim* — `top_face`, `h_inventory`, `coeff_inventory`,
`full_basis_gauge_audit`, `build_full_spec`, `native_builder_text`,
`write_system_from_rows`. Exactly one function is replaced: `closed_form`,
by the `Φ_eff` map of §2, which agrees with the charged one on every `s'=2` row
(CONTROL A2) and extends it to `s' ≥ 3`. Artifacts are written under
`box/moh14-20260905/charts/`; the charged instrument's own directory is never
written to.

**The threshold.** This is the one place where the `s'=2` formula cannot simply
be carried over, and getting it wrong would be a FALLACY-v2
*floor/attainment* error in the direction that invalidates kills.

The chart's monomial inventories are cut by `ord h(σ) ≥ B`, and for `s' = 2` the
charged instrument uses `B = V'_2 δ'_1 + u' δ'_2`: the `V'_2` central roots of
`h` separate from `σ` at `δ'_1`, and each of the `u'` outer roots at `δ'_2`,
because at `s' = 2` there is only one outer disc. **At `s' ≥ 3` that is false.**
The outer roots are distributed over `D'_2, …, D'_{s'}`, so an outer root
contributes some `δ'_j` with `2 ≤ j ≤ s'`, and since the radii increase inward
(`δ'_{s'} < ⋯ < δ'_1`) the true order can be *smaller* than
`V'_2 δ'_1 + u' δ'_2`. Using `B_tight` would cut monomials that are in fact
admissible — a strict sub-slice, exactly the error 17(ggggg) flags, and a
`SATURATED-EMPTY` on a sub-slice is not a kill.

The threshold this lane uses is therefore the weakest correct one:

```text
ord h(σ)  ≥  V'_2 δ'_1 + u' δ'_{s'}  =:  B_safe   ≤   B_tight ,
```

assigning every outer root the outermost radius. `B_safe < 0` on **14/14**, so
every row is inside the chart's scope. By contrast `B_tight ≥ 0` on rows 5, 6,
7, 8, 10 — five of the fourteen would have been rejected outright by the charged
scope test `B < 0`, which is a further sign that `B_tight` is the wrong object
here. The price is size: the safe inventories are strictly larger, and that is
paid in §5.

### 5.2 The cone (weighted-dehomogenisation) kill — licensed, with a control that fired

The chart's solution set is invariant under `(x,y) → (tx,ty)`, which grades the
parameters by

```text
w(h_{a,b}) = K' − a − b ,   w(A{i}_{a,b}) = w(B{i}_{a,b}) = i·K' − a − b ,
w(slope)   = 0 ,            w(c) = n' + m' − 2 − ℓ ,
```

and the row emitted at `(h_power hp, x_power xp, y_power yp)` must then be
`w`-homogeneous of degree `n'+m'−2 − hp·K' − xp − yp`.

`CONTROL_H` checks this **on every generator**, exactly, in Python:

```text
CHART r90_60_18_M2_9_V3_8_part_3_full  vars=88 gens=261 w(c)=26
  CONTROL_H     PASS   generators=261  inhomogeneous=0
  CONTROL_H_NEG PASS   (perturbed generator (h_0_5*h_0_5+h_0_5) is inhomogeneous)
```

All three partitions pass on all 261 generators. This is a free independent
validation of the charged emitter as well as the licence for the kill: since
`w(c) = 26 > 0`, over `k̄` any solution with `c ≠ 0` rescales to `c = 1`, so

```text
V(I) ∩ {c ≠ 0} = ∅   ⟺   1 ∈ (I, c−1) ,
```

and `reduce(1, std(I, c−1)) == 0` **over Q** is an exact char-0 unit
certificate — no modular step and no properness argument, per
[[homogeneous-cone-unit-test]] / [[k4ray-chart-grading-and-kill-test]].

A note worth banking: the first version of this control used `homog(I, W)` in a
`dp` ring and returned `CONTROL_HOMOG_FAIL` — that is not Singular's
weighted-homogeneity signature. It was diagnosed (an exact per-term degree
computation showed the generators homogeneous of the predicted degree), not
worked around. `wp(W)` also needs strictly positive weights, so it is unusable
on the partitions carrying slope variables (`w = 0`); hence the shipped control
