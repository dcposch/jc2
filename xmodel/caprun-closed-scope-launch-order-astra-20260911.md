# Closed-scope launch ordering — design only

Status: STATIC ADMINISTRATIVE DESIGN; no script, source change, enabled registration, worker or execution. First action 2026-09-11 09:06:01 UTC. Original publication reserve09:17 / hard09:20 UTC, unchanged. Basis0d39df3c9fd69c939a8420c54d03228b9077777d.

## Outcome and the actual circularity

Use one bounded, ROOT-owned admission holder as the initial main process of the eventual unit. After external ROOT installs and authenticates the final physical registration, the holder replaces itself with the exact registered dispatcher invocation. It never starts the dispatcher as a child. This is the smallest proposed ordering change: one unit, one main-process identity across exec, nine initially empty leaves, one final registration installation, one release. It requires a narrowly reviewed administrative launcher adaptation; the five frozen inputs are not edited here.

The current outer launcher requires the unit cgroup absent, arms timers, and immediately launches the dispatcher. The new registration requires actual outer/leaf dev/inode identities and nine pre-existing leaves before that dispatcher can admit its first phase. Separately, the old setup refuses unresolved registration placeholders and installs ROOT-REGISTRATION.json before launch. Renaming paths cannot satisfy both orders. Precreating an outer directory to guess the later unit identity contradicts the launch absence check; launching dispatcher early contradicts the guard; stopping/recreating a holding unit loses the identity being registered.

Split administrative installation from final registration installation and split unit admission from dispatcher exec. Keep the disabled template immutable in staging, not installed under the final registration pathname. During admission the final pathname remains absent. After all physical fields are known, install a NEW finalized copy once, not an in-place enablement of a file already consumed by a running dispatcher. The old stage/installed manifests that include registration likewise need a prospective two-stage materialization; their frozen originals remain historical templates.

## Admission-holder boundary, not a new supervisor

The holder is a future small, pinned administrative program, not supplied code. A root-only one-shot channel and a bounded shell builtin read are sufficient in principle; no sleep/poll-as-proof or background watcher is needed. Its channel belongs outside the science/wrapper exact-inventory directories and outside the batch output inventory. ROOT owns its directory0700 and controls its only authorized writer. The prelaunch commitment fixes the expected one-time token, unique unit name and exact eventual argv. The postcreation ROOT release record binds the actual InvocationID/PID/start, final registration SHA and all physical pins; those actual identities cannot be invented before unit creation. The holder need not parse registration or native manifests; authentication is the external ROOT/exclusive-writer boundary plus immutable final bytes, followed by the dispatcher's existing checks.

Opening the channel must not create an unbounded pre-timeout block; holder startup, wait and all exec errors remain enclosed by the already-running outer and absolute stop timers. The eventual implementation must define its EOF, timeout, partial/extra-token and duplicate-release refusals precisely. No general command text or environment values come from channel input. No eval, extra command substitution, forked dispatcher, signal-based unconditional continuation or release on mere file existence is admissible. A bad/missing release exits without dispatch. A root-only channel is administrative authentication under the accepted trusted-ROOT model, not protection from malicious root.

Immediately before exec, any holder-created helper must have been waited/reaped and all admission descriptors closed. Prefer no holder children at all. External ROOT queries/writers must remain outside the owned outer and must never attach to a leaf. The replacement exec chain clears the environment to exactly PATH=/usr/bin:/bin, LANG=C, LC_ALL=C and TZ=UTC and reaches the template's exact Python -I -S -B outer_argv at the same PID/start/cgroup. A transient env executable is an exec replacement, not a concurrent process; its installed path/native identity still requires ROOT qualification. Holder shell variables, startup files, signal dispositions, blocked masks, stdin and writable descriptors must not leak into the dispatcher. These are concrete obligations for the prospective launcher, not verified shell behavior here.

## Physical authentication and stable identity

The supplied physical-metadata template records the collecting process's PID namespace and the filesystem type. Neither that nor mountinfo alone proves the future holder/dispatcher sees the intended host hierarchy. Before release ROOT must bind actual DMI/instance/hostname/boot, unit InvocationID and ControlGroup, holder PID/start/PGID, actual holder root and PID/mount/cgroup/user namespaces to the authorized host context. It must compare the paths and directory identities as resolved in that actual process view with ROOT's view; authenticate its cgroup membership and ancestor tree, not just a spelling ending in system.slice. No private namespace, substituted mount, symlinked ancestry or narrower cgroup-root illusion is silently accepted.

Record outer device/inode as positive integers, exact holder-only direct membership, and the complete nine-name directory inventory. Outer and every leaf must be domain with empty subtree_control; each leaf has no child directories, no members and kernel populated0. Outer populated1 is expected from the holder and is not a setup failure. Record leaf device/inode, owner/mode/ACL and migration/delegation interfaces. ROOT must verify effective outer memory/swap/CPU/pids settings and no write path for workload UID/GID, no delegation or escaping writable descriptor. Empty subtree_control is an admission precondition, not permission to disable controllers in an existing scope. A different topology is STOP; do not prune, migrate, chmod an unrelated scope, restart or recreate to make it fit.

Keep that unit/holder alive while finalizing; do not use a separate temporary service, ExecStartPre unit with a different cgroup, or a stop/restart boundary. Its system manager configuration and all authorized root actors must respect the exclusive no-concurrent-migration/removal commitment until terminal custody. Recheck the same actual device/inode and membership immediately before release; do not substitute freshly created objects with the same paths. Stability comes from the controlled lifetime and absence of permitted movers/entrants, not repeated snapshots claiming atomic quiescence.

Native qualification remains a separate actual-installation obligation: exact interpreter/setpriv/runtime/native-manifest and source-native-subset hashes, aliases, directory inventories, absent paths and installed package/bytecode/cache facts under the selected startup flags. Pin the holder and environment-clearing executable as administrative launch inputs outside the runtime's fixed source inventories; they are not extra scientific roles. Nothing in these five inputs attests a future kernel, systemd, CPython build, namespace layout or native closure. No such observation occurred in this task.

## Clock, accounting and failure order

Preserve the old unit properties: RuntimeMaxSec3000, no randomized extra runtime, TimeoutStopSec5, control-group kill, memory8GiB, swap0, OOM kill, TasksMax32, CPU accounting/quota69%/10ms, normal scheduler, no realtime, Delegate=no and Restart=no. Keep source900wall/600CPU, batch3000wall/2100CPU/8GiB/128MiB and exact existing profiles. Nine-only remains nine-only. This plan adds no cap, liveness or aggregate enforcement theorem.

Unit active lifetime begins with the holder, NOT dispatcher exec. Every original absolute deadline/timer remains unchanged on release; holder time consumes available admission/outer time. The template's aggregate_cpu_start_usec="0" should remain zero for the newly created never-restarted cgroup so its total recorded CPU includes the holder and all later descendants. Do not replace it with the release-time cpu.stat value or treat exec as a new CPU origin. ROOT records the first available fresh-unit counter and subsequent counters, confirms the fresh lifecycle and installed accounting semantics, and rejects unexplained identity/counter reset. Counter snapshots are evidence, not permission to subtract admission work. External setup processes are separately bounded administrative work outside this unit, not disguised child CPU.

ROOT must choose one finite holder deadline strictly before the already-fixed admission deadline, leaving the existing phase wall+margin and terminal custody reserve; no particular UTC is invented here. A provisional120-second admission allowance is an UNMEASURED planning ceiling to fit inside those original bounds, not an increase, runtime forecast or authorization. If the final metadata cannot be frozen in that allowance, do not release. Even a valid token must not bypass an expired cutoff; the holder's bounded waiting contract and dispatcher's independent admission checks both remain necessary. The initial unit timers are not rearmed at exec.

Any holder death, final-registration/hash/namespace/topology mismatch, unexpected member, setup timeout, missing timer, failed exec or inability to prove the admission helpers gone means STOP/NO DISPATCH. Preserve the disabled template, failed candidate/final bytes and admission observations. ROOT's already-armed exact-unit TERM/KILL and worker-stop duties handle a stuck holder; no same-unit restart/retry or in-place repair is authorized. If dispatcher has begun, use its existing STOP/quiet/recovery contract; do not read a live science payload. Preserve source/native pre/post hashes, all terminal unit/PID/leaf evidence and durable byte custody before any leaf removal or output unmount. Cleanup is ROOT-only, exact-owned-target, terminal and separately authorized; this design performs none.
